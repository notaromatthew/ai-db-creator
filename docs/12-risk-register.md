# Risk Register

> **DRAFT / UNAPPROVED.** Likelihoods, frequencies and mitigations are planning assessments unless linked to frozen evidence. Review before pilot and at every material protocol change.

| # | Risk Category | Description | Likelihood | Impact | Mitigation Strategy |
|---|---|---|---|---|---|
| 1 | **LLM Hallucination** | The LLM generates tables, columns, or relationships that do not correspond to anything in the user's description or documents (e.g., inventing an "addresses" table when no address data is provided). This undermines trust and requires user intervention to correct. | **High** — observed in ~30% of test runs, especially with ambiguous or underspecified prompts. | **Medium** — users can edit or reject the schema via the chat interface and edit mode, but hallucinated entities waste time and may confuse non-expert users. | 1. Prompt engineering: add explicit "do not invent entities not mentioned in the source material" instruction. 2. Human-in-the-loop validation: every schema must be reviewed before database creation. 3. Provide document context explicitly in the prompt so the LLM has concrete data to ground its output. 4. Post-generation validation: automated check that every table name appears in or can be inferred from the source text. |
| 2 | **Poor Population Accuracy on PDFs** | PDF documents contain text that is poorly structured or contains rendering artefacts (line breaks in the middle of words, missing spaces, tables rendered as scattered text). LLM-based data extraction from such text produces high error rates. | **High** — PDF quality varies enormously; scanned PDFs yield empty text; complex PDF tables are often garbled. | **Medium** — the system still works well with CSV/Excel sources. Users with PDF-only data may get unusable results. | 1. Document parser returns empty text gracefully (user sees file listed but receives no data). 2. Instruct users to provide CSV/Excel as primary data sources. 3. Pre-processing: attempt table detection in PDFs using PyMuPDF's `get_text("blocks")`. 4. Future work: integrate OCR (Tesseract) for scanned PDFs. |
| 3 | **Participant Recruitment Difficulty** | Unable to obtain at least 34 completed participants in each of the Manual, AI-Only, and AI + Interface arms within the planned timeline. | **High** — the corrected RQ0/RQ3 design requires approximately 102 completers. | **High** — insufficient sample size reduces power and prevents confirmatory interpretation. | 1. Begin recruitment before expert evaluation ends. 2. Use several university and community channels. 3. Offer meaningful compensation. 4. Run a separate 5–8 participant formative pilot. 5. If the target is missed, report the study as exploratory; do not change design or target after inspecting outcomes. |
| 4 | **Low Inter-Rater Agreement** | Three expert reviewers produce ordinal Krippendorff's alpha below 0.67 on schema-quality dimensions. | **Medium** — schema quality is multidimensional and partly subjective. | **High** — low agreement weakens RQ1 conclusions. | 1. Provide anchored rubric examples. 2. Run a calibration session on practice schemas that are excluded from analysis. 3. Use ordinal Krippendorff's alpha with bootstrap intervals. 4. If alpha is below 0.67, revise the rubric or report individual ratings descriptively; do not replace ratings through post-hoc majority voting. |
| 5 | **LLM Provider API Changes** | OpenAI, Google, or another LLM provider changes their API in a breaking way (deprecates a model, changes output format, alters pricing terms) that breaks schema generation or population. | **Medium** — LLM APIs are evolving rapidly; deprecation notices are common. Pricing changes are likely. | **Low** — the system is provider-agnostic; switching to another provider is a configuration change. Some prompt tuning may be needed. | 1. Abstract all LLM calls through `_get_llm()` in `app/core/llm.py` with a uniform interface. 2. Support 5 providers (OpenAI, Google, Groq, OpenRouter, Ollama) so alternatives exist immediately. 3. Pin model versions in configuration (avoid `latest` or auto-upgrade). 4. Monitor provider status pages and deprecation schedules. 5. Budget for API costs explicitly; consider local Ollama as a free fallback. |
| 6 | **Scope Creep** | The project expands beyond the original research questions — adding more features, more LLM providers, more export formats, more document types — delaying the core research deliverables. | **High** — typical in PhD projects where technical development is inherently open-ended. | **Medium** — delays the thesis timeline; feature additions may never be used in experiments. | 1. Maintain a strict feature freeze after Phase 1. 2. Create a "future work" section in the thesis for desirable but out-of-scope features. 3. Prioritise research-ready stability over feature completeness. 4. Use GitHub Issues to track feature requests but batch them for post-thesis development. |
| 7 | **Reproducibility of Results** | LLM outputs are non-deterministic (even at temperature 0.0, many providers have inherent randomness). Running the same prompt twice may produce different schemas, making it difficult to reproduce experimental results. | **Medium** — temperature 0.0 reduces but does not eliminate variance. Different model versions give different results. | **Medium** — threatens the scientific validity of RQ1 and RQ2 findings. | 1. Set temperature = 0.0 for population and 0.1 for schema generation (lowest stable values). 2. Record the exact model version and settings with every schema generation (stored in interaction log). 3. Generate multiple runs (5 per condition) and report distributions, not single-point estimates. 4. Publish all generated schemas and populated databases as supplementary material. 5. Use the "gold-standard schema" comparison approach (RQ1) which is independent of LLM variance. |
| 8 | **Data Privacy / GDPR Violation** | Uploaded documents may contain personal data (names, addresses, financial information). The interaction logger captures all user actions. If participants are EU residents, GDPR requirements apply. | **Medium** — depends on dataset content and participant location. University ethics committees will flag this. | **High** — legal and reputational risk; could invalidate the entire study. | 1. All uploaded documents are stored locally and never sent to external servers (LLM API calls send extracted text, not raw files; for Google Gemini, check data handling policy). 2. Interaction logs contain event types and timestamps only, no personally identifying information. 3. Informed consent forms explicitly describe what data is collected and how it is handled. 4. Pseudonymise participant data: use participant IDs, not names. 5. Provide a data deletion option upon participant request. |
| 9 | **SQLite File Corruption** | The project's SQLite database files become corrupted due to concurrent writes (API + Celery worker), abrupt shutdowns, or disk errors. | **Low** — SQLite is robust for single-writer workloads. The application is single-user so concurrent writes are rare. | **Medium** — losing a project's database means the participant's work is lost. | 1. Auto-backup before every destructive operation (population, write query, SQL import). 2. Store backups in a separate directory from the live database. 3. SQLite WAL mode for better crash recovery (not yet implemented; documented as future work). 4. At least 3 recent backups always retained. |
| 10 | **Frontend-Backend Incompatibility** | API changes in the backend are not reflected in the frontend, or vice versa. This can happen during active development when both are modified independently. | **Medium** — common in full-stack development without strict API contracts. | **Medium** — users see broken UI (e.g., "TypeError: Cannot read properties of undefined"). | 1. Share TypeScript types between frontend and backend (Pydantic models are source of truth). 2. Run integration tests before each experiment session. 3. Version the API with a prefix (currently `v1` is implicit; consider `/api/v1/`). 4. Frontend should gracefully handle missing data (null checks, loading states). |
